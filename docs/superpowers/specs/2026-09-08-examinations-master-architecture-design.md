# Sathyagrahi Academy — Examinations Master Architecture Design

Date: 2026-09-08  
Status: **Design complete — awaiting final user review**  
Scope: Sathyagrahi Academy Admin + Student Examination System  
Repository: `sathyagrahiacademy-dotcom/Sathyagrahi-academy`

## 1. Purpose

This document is the master design for the Sathyagrahi Academy Examination Branch. It consolidates the previously approved examination-management, question-bank, auto-mapping, blueprint, result, performance, communication, PDF, audit, and student-attempt decisions into one operator-focused architecture.

Where this document conflicts with an older examination spec, **this master design is the source of truth for the final examination workflow**.

The central principle is:

> **One exam = one complete, traceable academic workspace from creation to archive.**

The system must be easy for one Academy operator to run daily, while preserving enough structure, safety, auditability, and version history to scale later.

---

## 2. Non-Negotiable Design Principles

1. Stable production must not be rebuilt from scratch.
2. Existing working examination, performance, communications, and student-portal flows should be extended, not replaced casually.
3. Academic history must never be silently overwritten.
4. Student exam passwords are student-entry credentials, not Admin authorization.
5. Exam status is system-driven; arbitrary manual status editing is not allowed.
6. Question mappings must use approved canonical syllabus entities; no silent fuzzy mapping.
7. Published/live academic data receives progressively stronger edit locks.
8. Result corrections create new versions; old valid history remains preserved.
9. Generated academic PDFs are immutable snapshots; corrections create new versions.
10. Every destructive or academically significant action is auditable.
11. Daily Tests use flexible student start times, not a fixed common start time.
12. Result publication timing is independent of the individual student attempt countdown.

## 7. Daily Test Attempt Timing — Flexible Start Model

Daily Tests are designed for students writing from home with different personal situations.

### Core rule

A student may start an available Daily Test at any allowed time while the exam is open for new starts.

Once the student presses **START EXAM**:

- The personal countdown begins immediately.
- Example: `45:00 → 44:59 → ... → 00:00`.
- The countdown cannot be paused.
- Closing the browser does not pause it.
- Logging out does not pause it.
- Changing device does not pause it.
- Re-login resumes the same server-authoritative remaining time.
- At `00:00`, the attempt auto-submits.
- Manual final submit closes the attempt immediately.

The timer is server-authoritative, not based on the student device clock.

### Result timing is separate from attempt timing

Result publication has two modes:

#### MANUAL

Admin chooses `PUBLISH RESULTS`.

At that point:

- New starts are closed.
- Students who never started become **ABSENT**.
- Any currently active valid attempt is allowed to complete its already-started full countdown.
- Result publication waits for those active attempts to finish or auto-submit.
- Then grading validation and result publication proceed.

#### SCHEDULED

Admin sets a result publication date/time.

At the scheduled publication time:

- New starts are closed.
- Students who never started become **ABSENT**.
- Students already in progress continue their existing full countdown without interruption.
- Result publication is held until active valid attempts finish or auto-submit.
- Then all ready results are published.

This prevents answer leakage while preserving fairness for students who already started.

### Student exam card

The card should communicate:

- Exam Available
- Start Anytime while available
- Duration
- Once Started: No Pause
- Result: Manual or Academy Scheduled Publication

It must not imply a fixed common start time when none exists.

## 10. Technical Reset, Reassignment, and Re-Exam

### Remove Assignment

Allowed only when the student never started the exam.

### Technical Reset & Reassign

For a faulty/invalid technical attempt:

- Remove faulty attempt data
- Remove faulty responses
- Remove faulty result
- Remove faulty performance rows
- Reset assignment/access
- Reuse the same exam, code, questions, and student password policy

A technical reset does **not** consume academic attempt sequence `E1/E2/E3`.

### Re-Exam

Used when a valid academic attempt already exists and the Academy grants another attempt.

Attempt labels:

- E1 — Original
- E2 — Re-Exam 1
- E3 — Re-Exam 2
- etc.

Rules:

- Same exam code
- Same syllabus/questions unless a separately approved corrected exam revision applies
- Prior valid answer/result/performance history is preserved
- Latest valid attempt is primary in the student experience
- Older valid attempts remain available to Admin and in attempt history

Resetting a valid academic attempt is exceptional and requires strong confirmation.

## 12. Absent Rules

A student is **ABSENT** only when:

1. The student was assigned to the exam,
2. The result-release process has closed the exam for new starts,
3. The student never created a valid attempt,
4. The student is not in a validated Technical Issue state.

Do not create a fake `0/total` academic result merely to represent absence.

Absence is a distinct exam-participation state.

## 13. Invalid Question Policy

If an exam question is declared academically invalid:

> **INVALID QUESTION = REMOVE FROM SCORING**

Effects:

- No +4
- No −1
- Correct/incorrect state for that question does not count toward grading
- The question is removed from the effective maximum marks
- Percentage is recalculated against the revised effective maximum
- Subject/topic performance is recalculated
- All valid attempts are regraded consistently

Example:

- Original: 45 questions, 180 marks
- One invalid question: 44 valid questions, 176 effective maximum marks

Scorecard clearly shows:

- Invalid Questions
- Effective Maximum Marks

### Timing-specific behavior

**Live:** no direct content edit; Admin may mark a question invalid.

**Conducted, results unpublished:** invalidate → regrade all → recalculate performance → Results Ready.

**Result already published:** create corrected result revision and revised PDFs; preserve old version.

## 29. Automatic Lifecycle Status Engine

Status is derived, not freely typed.

### Core states

- **Draft** — setup incomplete
- **Ready** — required setup complete and validated
- **Available / Upcoming** — published and open for student access/new starts
- **Live** — one or more students currently have active attempts
- **Conducted / Closed** — closed for new starts as part of result-release flow and all active attempts have finished
- **Results Ready** — grading completed but results not yet student-visible
- **Result Published** — student-visible results released
- **Archived** — Admin archival action

Because Daily Tests use flexible starts, `Live` is an attempt-driven state rather than a fixed common-clock state.

### Allowed Admin/system transitions

- Publish
- Unpublish where academically safe
- Close for Result Release
- Archive
- Restore
- Correction

A manual arbitrary status dropdown is not provided.

## 33. Error Handling and Recovery

The system must fail visibly, not silently.

### Question/import/mapping failures

- Exact row/question error
- No silent partial success
- Publish remains blocked until required validations pass

### Attempt sync failure

- Student sees `Pending Sync`
- Server preserves already-saved answers
- Final submit attempts a final synchronization/verification
- Auto-submit uses server-saved state

### Grading failure

- Result is not published
- Action Required alert created
- Retry is Admin/system-controlled and idempotent

### Communication failure

- Delivery logged as failed
- Action Required alert created
- Retry should not duplicate an already-sent mail

### PDF generation failure

- Academic result remains valid
- File generation marked failed
- Action Required alert created
- Regeneration produces the missing version, not a silent overwrite

## 34. Data Integrity Boundaries

The design should keep these concepts separate:

1. **Question Bank Master** — reusable editable repository
2. **Exam Question Snapshot** — immutable exam-time copy
3. **Student Attempt** — one technical or academic attempt record
4. **Student Responses** — answer evidence tied to attempt
5. **Result Version** — graded academic outcome
6. **Performance Evidence** — derived from valid mapped result evidence
7. **Generated File Version** — immutable document snapshot
8. **Communication Delivery** — idempotent outbound delivery state
9. **Audit Event** — immutable significant-action history

This separation prevents later edits in one layer from mutating historical evidence in another.

## 35. Canonical Syllabus Administration

All question and performance mapping depends on canonical syllabus IDs.

Rules:

- Subject / Unit / Chapter / Topic hierarchy is centrally maintained.
- Imports and manual questions reference canonical hierarchy.
- Safe exact normalized matching may auto-map.
- Uncertain matches require explicit review.
- Historical exam mappings remain stable even if display labels are corrected later; ID history and migration must be controlled.

A future broader syllabus-version administration feature may be designed separately if annual NEET/NCERT structure changes require it.

## 37. Operator End-to-End Workflow

`Create Exam → Coverage → Questions → Mapping → Blueprint → Audience → Publish`

### Student side

`See Available Exam → Enter Password → Start Anytime → Personal Countdown → Save Answers → Final Submit / Auto-submit`

### Admin during attempts

`Monitor Assigned / Not Started / In Progress / Submitted / Technical Issue`

### Result release

Manual:

`Admin Publish Results → Close New Starts → Mark Never-Started as Absent → Wait for Active Attempts → Grade/Validate → Publish`

Scheduled:

`Scheduled Release Time → Close New Starts → Mark Never-Started as Absent → Wait for Active Attempts → Grade/Validate → Publish`

### After publication

`Student Result → Answer Review → Performance → Scorecard → Question Paper → Marked Answer Paper → Result + Daily Performance Email`

### If correction needed

`Correction Action → Reason → Regrade All Affected Attempts → Result v2 → Revised Performance → Revised PDFs → Optional Student Notification`

### Long-term history

`Conducted → Monthly History → Archive → Retain Results / Performance / Credentials / Audit / Files`
